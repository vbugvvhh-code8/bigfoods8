# BigFoods POS Audit — 11 November 2026

## Scope and method

Static review of the current `main` implementation. Reviewed the cashier screen, POS catalogue, order history, analytics, reports, staff/Edge Function action handlers, and POS catalogue/sales migrations.

This is a code-level audit, not a completed runtime or live-payment test. Findings below are confirmed from the implementation unless explicitly marked for verification.

## Executive summary

The POS foundation is present: staff-session authorization, a separate BigFoods catalogue, cart and quantity controls, cash and physical Moniepoint checkout, receipt numbering, idempotency keys, sales history, CSV export, analytics, and audit-event logging.

The highest-risk gap is that a sale header and its line items are written in separate database operations rather than one atomic transaction. The code does mark a sale `needs_review` if line insertion fails, but this can leave a paid/recorded header without its items. The next priority is inventory deduction and reconciliation: catalogue stock metadata exists, but checkout does not decrement or reserve stock, and recipe-linked inventory is not consumed by POS sales.

## Findings

### P0 — Checkout header and line items are not atomic

- **Evidence:** `supabase/functions/bigfoods-inventory/index.ts`, action `pos_sale_create`.
- The handler inserts `bigfoods_pos_sales` first, then inserts `bigfoods_pos_sale_items` in a separate request.
- If line insertion fails, the header is changed to `needs_review` and the API returns 503. This is a useful safeguard, but it is not an atomic checkout.
- **Risk:** incomplete sale records, reconciliation work, and uncertain retry handling after a payment has already been accepted.
- **Recommended fix:** move validation, sale header, sale lines, stock deduction, and audit event into one Postgres RPC/transaction. Preserve idempotency at the database boundary and return the existing complete receipt on retry.

### P1 — POS sales do not deduct or reserve inventory

- **Evidence:** `pos_sale_create` reads product price/availability and writes sales; it does not update `stock_quantity`, inventory batches, or inventory movements.
- POS catalogue supports `stock_quantity`; recipe/inventory linkage also exists elsewhere, but the sale path does not consume it.
- **Risk:** overselling, stock-on-hand drift, and food-cost/margin reporting that cannot be reconciled to actual ingredient usage.
- **Recommended fix:** define whether stock is tracked as finished-product quantity, recipe ingredients, or both. Deduct through atomic inventory RPCs, reject insufficient stock, and record immutable movements.

### P1 — Catalogue options/modifiers are not carried into the sale

- **Evidence:** catalogue schema includes `option_groups`; the cashier cart stores only product and quantity, and checkout sends only `product_id` and `quantity`.
- **Risk:** customers cannot select configured sizes, add-ons, variants, or paid extras; receipts and revenue omit those selections.
- **Recommended fix:** implement modifier selection in the cart, validate option IDs/prices server-side, and snapshot selected options and price adjustments into sale lines.

### P1 — Discount UI is a non-functional placeholder

- **Evidence:** `app/staff/pos/page.tsx` has an Apply button that displays “POS discount codes are not configured yet”; checkout does not send a discount and the server computes subtotal = total.
- **Risk:** the interface suggests a discount action that cannot complete; there is no authorized discount or promotion audit trail.
- **Recommended fix:** either remove the control until supported or implement server-validated fixed/percentage discounts, eligibility, expiry, limits, approval permissions, and immutable discount snapshots.

### P1 — Void/refund lifecycle is not implemented in the POS workflow

- **Evidence:** sales schema has statuses `paid`, `voided`, `refunded`, and `needs_review`; the order page can filter statuses but no POS void/refund action was found in the reviewed UI or Edge Function actions.
- **Risk:** mistakes and returns cannot be corrected through a controlled, auditable cashier workflow.
- **Recommended fix:** add manager-authorized void/refund actions, reason codes, payment reversal/reconciliation references, audit events, and compensating inventory movements. Never delete historical sales.

### P1 — Receipt handling is incomplete

- **Evidence:** cashier UI explicitly says receipt email delivery is not connected. The success receipt only displays a small summary; printing calls `window.print()` on the current POS page rather than a dedicated receipt layout. Order details expose two print/receipt buttons that call the same print action.
- **Risk:** no reliable customer receipt delivery or consistent print output for counter handoff and reconciliation.
- **Recommended fix:** create a print-optimized receipt view with business identity, receipt number, timestamp, cashier, item/modifier lines, subtotal, discount, tax (if applicable), total, payment reference, cash received/change, and customer details. Add email delivery with retry/status tracking if required.

### P1 — Reports and analytics are POS-only, not unified

- **Evidence:** analytics/reports pages explicitly state online orders and customer/inventory reporting are excluded. Orders page also says online orders are not connected.
- **Risk:** management cannot use these pages as a complete BigFoods sales or business-performance view.
- **Recommended fix:** define a unified reporting model with source/channel dimensions before combining online orders and POS transactions; avoid double-counting payment records.

### P2 — Customer management is only a placeholder

- **Evidence:** POS sidebar Customers action only displays a notice; checkout stores optional customer email, not a customer record, phone number, name, loyalty profile, or customer history.
- **Risk:** repeat-customer identification, customer lookup, loyalty, and CRM workflows are unavailable.
- **Recommended fix:** connect a customer directory and allow cashier lookup/create, with optional name/phone/email and privacy controls.

### P2 — Cashier attribution in order details needs correction

- **Evidence:** the order detail panel displays the currently signed-in staff name (or selected sale's cashier ID fallback) rather than resolving the selected sale's `cashier_staff_id`.
- **Risk:** historical orders viewed by another cashier can show the wrong cashier identity.
- **Recommended fix:** return the cashier display name for each sale from the authorized server action and render that sale-specific value.

### P2 — Date boundaries use UTC rather than Nigeria local time

- **Evidence:** `pos_sales_list` and `pos_sales_summary` append UTC midnight to date filters. The UI displays dates in the `en-NG` locale.
- **Risk:** transactions around midnight can appear in the wrong selected business day for a Nigeria-based operation.
- **Recommended fix:** use an explicit business timezone (e.g. Africa/Lagos) and convert local date boundaries to UTC consistently on the server.

### P2 — Analytics/report summary can become incomplete at scale

- **Evidence:** `pos_sales_summary` reads the matching sales set without pagination or a database aggregate; the report exports the returned `sales` array.
- **Risk:** large periods may be capped by the PostgREST row limit, causing under-counted totals and incomplete CSV exports.
- **Recommended fix:** calculate aggregates in SQL and paginate export data or generate a server-side export with explicit row counts.

### P2 — Payment reconciliation data is insufficient

- **Evidence:** payment methods are cash and physical Moniepoint terminal. Terminal completion is a cashier checkbox; no terminal transaction/reference ID or settlement reconciliation record is captured.
- **Risk:** the system relies on manual attestation and makes disputes, duplicate terminal charges, and settlement matching harder to resolve.
- **Recommended fix:** capture terminal reference/approval code and reconciliation status. If no terminal API integration is available, make the manual confirmation flow explicit and require a reference number.

## Recommended implementation order

1. **Atomic checkout + idempotent recovery** (P0).
2. **Inventory deduction and stock validation** (P1).
3. **Modifier/options support with server-side price validation** (P1).
4. **Void/refund and payment reconciliation lifecycle** (P1).
5. **Real discounts or remove the placeholder** (P1).
6. **Receipt print/email workflow** (P1).
7. **Correct cashier attribution and Nigeria business-day filtering** (P2).
8. **Scalable reporting aggregates and complete export** (P2).
9. **Customer directory and unified online/POS reporting** (P2).

## End-to-end verification still required

- Apply all POS/staff/inventory migrations to a disposable test database and verify schema compatibility.
- Test role matrix: cashier/POS, manager, inventory, auditor, admin, inactive staff, and forced password change.
- Test cash exact amount, overpayment/change, underpayment rejection, and malformed values.
- Test Moniepoint confirmation, missing confirmation, reference capture, duplicate submission, and failed/ambiguous payment.
- Force a sale-line insert failure and verify there is no orphan/inconsistent sale.
- Test unavailable products, concurrent checkouts, stock depletion, and recipe ingredient deduction.
- Test discounts/modifiers, receipt printing/email, void/refund, date boundaries around midnight Africa/Lagos, and large report exports.
- Confirm Netlify Deploy Preview build and browser-based cashier workflow on desktop and mobile.

## Boundaries

No production data was changed. No database migrations were applied. No POS behavior was modified in this audit PR; this PR adds only this audit document. Findings should be revalidated against a live test environment before implementation decisions that depend on deployment configuration or database state.
